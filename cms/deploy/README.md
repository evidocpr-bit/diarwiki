# Эксплуатация CMS «ДиарВики»

Рабочую CMS нельзя открывать до завершения `cms/docs/preflight.md`. Сначала используется отдельный тестовый адрес, затем — `cms.diarwiki.ru`. PostgreSQL остаётся без хостового порта, Directus слушает только `127.0.0.1:8055`, TLS принимает Caddy.

## Секреты резервирования

Файл `/etc/diarwiki/backup.env` принадлежит root, имеет режим `0600` и не попадает в Git:

```dotenv
BACKUP_AGE_RECIPIENT=age1...
BACKUP_AGE_IDENTITY_FILE=/etc/diarwiki/backup-age-key.txt
BACKUP_RCLONE_DEST=remote:diarwiki-cms
RCLONE_CONFIG=/etc/diarwiki/rclone.conf
```

Закрытый ключ не должен быть единственной копией на сервере. Отдельно хранится офлайн-копия ключа и проверяется возможность расшифрования. Скрипт не считает резервную копию успешной, пока не расшифрует её обратно, не сравнит исходный архив и не подтвердит передачу `rclone` во внешнее хранилище. Локально хранятся 14 дней ежедневных и 8 недель воскресных копий. Удаление внешних копий автоматически не выполняется: срок хранения задаётся политикой самого защищённого хранилища.

## Первичная установка

1. Разместить проверенный checkout в `/opt/diarwiki`.
2. Создать `cms/.env`, `/etc/diarwiki/release.env` и `/etc/diarwiki/backup.env` с режимом `0600`.
3. Проверить доступность `age`, `rclone`, Docker Compose, Node.js, pnpm и Caddy.
4. Запустить `install-cms.sh`, собрать расширения, затем поднять Compose.
5. Подключить `Caddyfile.cms` к основной конфигурации Caddy и выполнить `caddy validate`.
6. Выполнить bootstrap схемы, политик и русской панели по `cms/bootstrap/README.md`.
7. Создать служебный токен выпуска, включить таймеры и выполнить `verify-cms.sh`.
8. Пригласить владельца, включить 2FA и только после проверки доступа приглашать остальные роли.

## Обновление

`update-cms.sh` отказывается работать с изменённым checkout, сначала создаёт подтверждённую внешнюю резервную копию, затем собирает расширения, обновляет контейнеры и проверяет CMS. Обновление версии PostgreSQL выполняется отдельным окном после тестового восстановления.

## Восстановление

Восстановление сначала выполняется на изолированном тестовом хосте:

```bash
cms/deploy/restore-cms.sh /srv/backups/diarwiki-cms/diarwiki-cms-YYYYMMDDTHHMMSSZ.tar.age --confirm-destructive-restore
```

Команда проверяет SHA-256 зашифрованного файла, безопасные пути архива, внутренние контрольные суммы, пересоздаёт базу и заменяет том медиа, затем запускает `verify-cms.sh`. Флаг подтверждения не заменяет проверку выбранного сервера и файла. В рабочем окружении перед восстановлением фиксируются причина, текущий выпуск и отдельная копия текущего состояния.

Ежеквартально проводится тестовое восстановление. В журнале фиксируются имя резервной копии, время начала и завершения, результат проверки входа, количество материалов и файлов, а также исполнитель — без паролей, токенов и содержимого закрытых подтверждений.
